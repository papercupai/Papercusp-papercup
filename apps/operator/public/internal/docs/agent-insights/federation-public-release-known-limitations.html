Federation public-release: known limitations + release-criteria gate

This is the honest release calibration for cross-machine peer-to-peer shared-pot federation: what is proven live (over real, separate machines on the public DHT), what is proven in-process only, the standing known limitations, the forceReFold mechanism + its cost, and the explicit public-release checklist — which of the federation-release-hardening briefs must be green before we can call federation shippable.

It deliberately supersedes the optimistic “FULLY WORKING + RELEASE-READY” claim (memory a02714f1) with the calibrated view (memory f64a176d, the calibration correction — read that one). The core path is real and reproducible; it is not yet at a defensible public-release bar. Read this before telling anyone federation is done.

The one rule this page exists to enforce: in-process green ≠ live green. The A→B owner-admit race passed every in-process test and still failed live. So an in-process-green scenario is necessary but not sufficient evidence — every release-gating scenario must be reproduced over real VMs, not just asserted in the in-process matrix.

The forceReFold mechanism + its cost

Section titled “The forceReFold mechanism + its cost”

forceReFold is the deterministic fix for the live A→B owner-admit timing race.

Root cause. The joiner (B) bootstrap-admits the owner’s (A’s) log during the home=<none> boot window. It folds A’s hive_members op through the member-slug-bound projection, so A’s roster row is dropped at projections/pot-members.ts (row.hive_home_slug !== member slug) and the merge cursor marks the op done. When the rekey rebinds the projections to the pot-home slug, retryPendingOnce only re-admits still-pending peers — it does not re-apply an already-admitted-and-folded op. Result: empty roster → A’s content defers forever.

The fix (packages/operator-core/lib/sync/hyperbee/boot.ts):

  1. A one-shot let forceReFold = false flag.
  2. Set forceReFold = true in rekey()’s rebind block, after the hive_members/hive_settings projections rebind from the member slug to the pot-home slug.
  3. Consumed at the top of the merge pass, under the merge gate: it resets the merge cursor (mergeCursor = createMergeCursor()) and clears the flag, so the next pass re-folds every admitted log through the now-pot-home-bound projection — A’s roster row re-applies and the deferred content drains.
  4. Driven by a terminal mergeNow() at the end of rekey() (this is what makes it deterministic, rather than depending on the 5s periodic tick — the latency that PAPERCUSP_A003_TRACE’s stderr delay accidentally flipped green in run31 vs the red run32).

Regression test: packages/operator-core/lib/sync/hyperbee/__tests__/owner-roster-rebind-race.repro.integration.test.ts (deterministic, RED-without / GREEN-with). Adversarial review verdict: SAFE TO SHIP — no CRITICAL/HIGH, race-freedom sound (the terminal mergeNow() always delivers the re-fold with the new binding), projections are LWW-guarded, revocation ordering correct, pendingMemberContent drain fires once (review record: memory 4d1db206).

The cost (and the one open follow-up)

Section titled “The cost (and the one open follow-up)”

forceReFold re-folds all admitted logs on each home-resolving rekey rebind. It is one-shot — the flag is cleared immediately under the merge gate, so steady-state passes are unaffected — but the re-fold itself is O(total ops across all admitted logs). At scale (many members, large logs, repeated rekeys) this is the thing to watch for a perf cliff; Brief 9 is characterizing it (in-process, since live many-member is blocked by the quota cap). No cliff/leak has been attributed to it yet.

Snapshot interaction — the gating follow-up (Brief 11). The forceReFold cursor reset is placed before seedCursorFromSnapshots. With FLAGS.SUBSTRATE_LOG_SNAPSHOT ON, the re-fold must still re-apply the dropped hive_members op (a snapshot op summarizes all current rows, so it should). An integration test covering forceReFold reset → seedCursorFromSnapshots with the snapshot flag ON must land before the log-compaction/snapshot flag ships. This is the only open review item.

9. Owner→joiner federation can stay broken in the pure NO-RESTART join path (RESOLVED — both mechanisms fixed + live-verified 2026-07-02)

Section titled “9. Owner→joiner federation can stay broken in the pure NO-RESTART join path (RESOLVED — both mechanisms fixed + live-verified 2026-07-02)”

A live run (Brief 6 attempt-1, su-e7698: 2-frame, shared forceReFold .deb, real DHT) surfaced owner(a)→joiner(b) content federation FAILING in the plain join→write path with no restart: b’s hive_members roster stayed EMPTY for 270s+, so decideMemberContentOp dropped every owner op (b→a was fine). Code root-cause (su-0f0a4): forceReFold (boot.ts) fires exactly once, on the rekey()→pot-home rebind, then resets. If the owner’s hive_members op arrives at the joiner after that single re-fold (during drain), it is never re-applied — it stays dropped-in-the-home-window until a restart or a later rekey. This is consistent with Brief 5 (restart) PASSING (the restart re-folds) and means the earlier “proven live” runs (run33/34/35) may have included a restart/rekey rather than exercising the pure no-restart path.

Root cause (confirmed, su-2c799): cross-process opStateCache staleness under SUBSTRATE_SIDECAR. join-pot.ts (MAIN process) commits the registry (remote_hive:true + hive_slug) and invalidates its OWN cache; but rekey() runs in the substrate SIDECAR process, whose warm harness_registry cache (2s TTL, kept hot by the sidecar’s constant reads) never saw that invalidation → it serves the STALE pre-join value → joinerHiveHomeSlug returns null → resolveHiveHomeProjectionSlug returns null → next===prev(null) → the rekey rebind block (boot.ts ~2599) SKIPS → forceReFold never fires → the member-slug projection binding latches → the owner’s hive_members rows drop forever → roster EMPTY. A restart cold-reads fresh at boot → binds correctly (why Brief 5 restart PASSED). Neither original candidate — it was a third mechanism (stale cross-process cache read at the resolve, not a re-fold-coverage or rebind-timing bug).

Status: FIX LANDED (su-2c799, WI-1378). resolveHiveHomeProjectionSlug now calls joinerHiveHomeSlug(ws, slug, { fresh: true }), threaded through loadHarnessRegistry({fresh}) → readOperatorState({fresh}) to BYPASS the 2s cache on this one rare resolve path (hot-path callers keep the cache, so the seqscan perf win is preserved). A fresh PG read is guaranteed to see the committed write (join-pot awaits the mutateRegistry commit before the rekey RPC). Second mechanism (WI-1544, the race bifurcation): when the deterministic join-time binding resolved BEFORE the owner’s announce, the joiner’s pot-home projection conclusively rejected the owner core on the slug filter (origin=member-slug), membership chicken-and-egged, and A→B blacked out permanently (the rekey rescue was structurally unreachable — no binding transition). Fixed in boot.ts: inJoinBootstrapWindow() reclassifies a join-window binding_invalid as retryable/buffered instead of conclusive-reject, and the scope_unresolved buffer holds out-of-scope slug-filter frames while the pot-home projection slug is unresolved (WI-1544, resolved 2026-07-02; 41 dedicated tests in boot.test.ts + announce-channel-multihive.test.ts).

Live verification: matrix run m1783013203 (2026-07-02) federated A→B on the FIRST poll across all 8 scenarios — no restart, no adaptive re-fold rescue needed. This limitation is closed.

11. Boot-window / silent-re-federation data-loss class for CDC-captured tables (WI-5441) — CONSCIOUSLY WAIVED for public release (2026-07-25, WI-5764)

Section titled “11. Boot-window / silent-re-federation data-loss class for CDC-captured tables (WI-5441) — CONSCIOUSLY WAIVED for public release (2026-07-25, WI-5764)”

Symptom (demonstrated live, 5+ independent repros across 2026-07-18/19): a row written on the origin peer occasionally federates with zero corresponding harness_shared.substrate_outbox entry, ever — the write is silently and permanently non-federating, with no error, no stall-detect signal, and no reconciliation pass to catch it. First reproduced on plan_item_assignments (the generic capture_substrate_outbox() capture path, migs 359/446); the mechanism is not table-specific, so any table riding that generic capture function is exposed in principle — most consequentially harness_shared.work_items (features/issues), which rides the sibling capture_work_items_outbox() function (mig 375/423) and was flagged at filing time as the path where this class would be most damaging (the shared-pot editing surface). No work-items-family repro has been observed; this is a structural risk, not a demonstrated second instance.

What is CONFIRMED, after an exhaustive multi-session investigation (WI-5441 posts, 2026-07-18 22:03 → 2026-07-19 17:10, 5+ agents):

  • The federation-capture trigger (capture_substrate_outbox_trg) is always attached and enabled well before the losing write in every repro — a “trigger not yet attached at boot” race was directly falsified by OID/timing forensics on 3 separate runs.
  • No online-guard, no session_replication_role override, no ON CONFLICT short-circuit, no swallowed exception, and no GC-deletion timing explains a bare local-origin INSERT losing its capture entry.
  • The clearest live-caught instance (real production content, plan health-tab-v2-2026-07-12 items P-013–015, not the synthetic seed probe): a row’s origin flips remote→local with byte-identical federated content (no assignee/assigned_ts/strategy/note change) and produces no outbox row — i.e. something re-applies an already-materialized op through the projection’s writeToPg with a provenance context that resolves origin to 'local' on a write that is not actually a fresh local edit. The leading (unconfirmed) hypothesis is a periodic reconciliation/re-fold pass constructing OpEnvelopes directly from DB rows rather than from a peer-log op, without threading provenance — see WI-5441 post 52971 for the exact code seam to instrument (writeToPg’s provenance?.origin ?? 'local' fallback, packages/operator-core/lib/sync/hyperbee/projections/ plan-item-assignments.ts).
  • Root-cause identification requires live rig instrumentation (a debug capture trigger armed from before boot) — static code reading across every receive-side call site (own-log snapshot compaction, backfill-local-state, the epoch decrypt gate, withHiveHomeApplyGuard, resolveOpProvenance’s fallback) has been exhausted without a positive catch of the exact writer; see WI-5441 posts 52968/52971/52980 for what has been ruled out and why.

What WAS fixed 2026-07-25 (WI-5764, defensive hardening — NOT proven to be this class’s root cause): a genuinely real, separate boot-ordering race was found and fixed in the native :5432 operator host path (apps/operator/bin/hono-host.ts + host-bootstrap.ts): startRequestServers() previously ran unconditionally immediately after the fire-and-forget runBootstrap() call, with no ordering guarantee against the still-running migration apply — so an HTTP write could in principle reach a table before a still-applying migration set had created its capture trigger. Fixed by gating startRequestServers() on a new boot-gate flag (markMigrationsAppliedForRequestGate/awaitMigrationsAppliedForRequestGate, packages/operator-core/lib/sync/hyperbee/boot-gate.ts) that flips the instant applyPendingMigrationsAtBoot() returns; a request-only host (PAPERCUSP_BACKGROUND_WORKERS=0) or a timeout degrades open (log + serve anyway) so this can never wedge boot. Caveat found while implementing this fix, worth recording explicitly: the live-fed-gate / local-matrix rig that produced every WI-5441 repro above boots the desktop/embedded-pg entrypoint (apps/operator/bin/serve.ts → startEmbeddedPostgresServer), which awaits its own migration-apply step to completion before runBootstrap() or serve() ever run — so that specific race does not explain the observed reds (consistent with WI-5441 post 52911’s own finding that the capture trigger already existed ~4 minutes before the losing write in that repro). The hono-host.ts fix is real, low-risk, and worth having (it protects the native :3070/:3170 dev-box hosts, a different boot path with the same class of race), but it is not the fix for this section’s demonstrated defect — treat the two as separate, both real.

The waiver. Given (a) the mechanism is narrowed but not pinned without a dedicated live-instrumentation session, (b) every prior attempt at that session was resource-constrained by the shared single-tenant rig, and (c) no second instance has been observed on the work-items family despite it being structurally exposed — this class ships as a known, documented limitation for the public release, not a release blocker, on the following basis:

  1. It requires a specific, uncommon interleaving (a re-apply of already-correct content racing the capture path) — not a routine write path failure.
  2. The loss is confined to metadata/assignment-shaped federated tables observed so far (plan_item_assignments); no core content (features/issues/plans/coord threads) loss has been demonstrated.
  3. The durable fix direction is known (WI-5441 post 52911): a reconciliation pass that compares TABLE STATE across peers for CDC-captured tables (rows present on the publisher, absent/stale on the joiner) rather than trusting outbox history alone — this is a bigger, higher-risk change (a new periodic cross-peer state-diff mechanism) appropriately scoped as its own follow-up, not something to rush unattended against the release-critical gate rig.

Tracking. WI-5441 stays open, blocked, claim-held with this waiver recorded — do not silently re-close it as resolved. Any future session with a free rig slot should pick up the live-instrumentation step exactly where post 52980 left off (a fresh rig with BOTH an INSERT and UPDATE debug trigger armed from before boot, per the first WI-5441 checkpoint).

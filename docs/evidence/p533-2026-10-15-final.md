# Hyperdisk Balanced / AWS io2: 50 Luna-low storage comparison

Status: Google and AWS native measurements are complete, and the final AWS teardown census is empty. The resumed AWS run completed 250/250 wakes with zero failures. This is the completed P-533 evidence draft.

## Recommendation supported by the completed Google measurements

Use zram first for parked agent memory, with Hyperdisk Balanced as overflow when compressed RAM is insufficient. Keep the database and disk swap on separate volumes for the measured competing-I/O workload. Retain the default disk swap readahead setting (`vm.page-cluster=3`) on this configuration: setting it to zero made input response worse in this run. These are benchmark recommendations; no production settings were changed.

The owner-selected fresh-trial allocation is OS 32 GiB, database 256 GiB and swap 256 GiB. The DB capacity alone costs $20.48/month on Google Hyperdisk Balanced or $32/month on AWS io2. Provisioned performance, particularly io2 IOPS, can cost substantially more than capacity. The measured existing shared development cluster was about 246 billion bytes across 34 databases; its 384/512 GiB headroom recommendation is separate from this fresh-trial choice.

Hyperdisk Balanced starts at 4 GiB, with 2,000 fixed IOPS at that size; 5 GiB has 2,500 IOPS. At 256 GiB it can provision up to 128,000 IOPS, subject to the VM limit. The tested C4 eight-vCPU VM supports at most 50,000 IOPS / 800 MiB/s across its Hyperdisk Balanced volumes. A small disk therefore avoids the Titanium whole-shape storage purchase, but cannot obtain every advertised maximum independently of size and host.

AWS's cheaper gp3 alternative starts at 1 GiB and includes 3,000 IOPS / 125 MiB/s. Current standard-region specifications permit up to 80,000 IOPS / 2,000 MiB/s, with size, IOPS and host restrictions; AWS describes its latency as single-digit milliseconds. All io2 volumes are now Block Express; on Nitro, AWS specifies average latency below 500 microseconds for 16 KiB operations and volume ceilings of 256,000 IOPS / 4,000 MiB/s. Those published averages and ceilings are different quantities from this trial's 4 KiB median at queue depth one. gp3 was researched, not measured as a 50-agent data-swap arm.

## What was exercised

The maintained `scripts/agent-capacity/vm/swap-tier.py` driver launches real Codex 0.162.1 foreground interactive sessions, `gpt-6-luna`, low effort. Each session has its own measured systemd cgroup, executes real dummy-file reads and SHA-256 checks through the native sandbox, and must settle its native task with the expected assistant response. No synthetic resident-memory padding or fake inference was used. Upstream credentials stayed on the controller behind a private loopback SSH forward.

Google: C4 standard-8, eight vCPUs, 30 GiB RAM, Ubuntu kernel 7.0.0-1014-gcp; 256 GiB Hyperdisk Balanced swap at 16,000 provisioned IOPS / 400 MiB/s. Fifty sessions completed six warm-up rounds. Each storage arm then woke all 50 together; swap arms explicitly reclaimed their memory and idled for 60 seconds. Approximately 64 MiB per agent was swapped. This is a small dummy-session workload, not proof of 50 production Papercusp projects or long-idle capacity.

AWS: m7i.2xlarge, eight vCPUs, 32 GiB RAM; 256 GiB encrypted io2 at 6,000 IOPS. The final bounded trial retains the same six verified warm-up turns per session but limits concurrent warm-up requests to five after recorded upstream capacity errors. Wake storms still use all 50 sessions. This difference must remain visible in the comparison.

The completed resumed AWS run restored those six hash-verified warm histories, added one fresh native verification round (50/50), and then completed five 50-agent wake arms with zero failures: RAM, zram-lz4, zram-zstd, io2/page-cluster 3, and io2/page-cluster 0. On this resumed-context run, median storm input echo was 0.283 s (RAM), 0.306 s (lz4), 0.319 s (zstd), 0.938 s (io2/page-cluster 3), and 6.774 s (io2/page-cluster 0). The resumed sessions make these descriptive comparisons; they are not a fresh-process baseline.

For the tested 256 GiB total, 64 Google 4-GiB Hyperdisk Balanced volumes would cost the same $20.48 capacity charge as one 256-GiB disk, but each 4-GiB volume has fixed 2,000 IOPS and the C4 eight-vCPU host caps aggregate Hyperdisk performance at 50,000 IOPS / 800 MiB/s. AWS gp3 permits 256 1-GiB volumes at about $20.48 capacity-only, but the nominal per-volume 3,000-IOPS baselines are bounded by EC2 attachment and EBS host limits. AWS io2 requires 4 GiB: 64 4-GiB volumes at the 100-IOPS minimum would cost about $448/month ($32 capacity plus $416 IOPS), versus $38.50 for one 256-GiB volume at 100 IOPS or $422 for one at the tested 6,000 IOPS. Multiple swap devices can spread independent page traffic; they do not stripe each I/O unless a RAID/device-mapper layer is added, which increases failure and operational risk.

The Google warm-up experienced a private-forward interruption and recorded bounded provider-capacity retries. Restoring the forward let the existing run finish; all five later wake arms completed. End-to-end model reply times include inference availability and run-order effects, and must not be interpreted as pure SSD latency.

## Google 50-session result

| Arm | Successful wakes | Median input echo | Median complete reply | Fork/exec probe p99 |
|---|---:|---:|---:|---:|
| RAM | 50/50 | 0.221 s | 23.790 s | 1.40 ms |
| zram lz4 | 50/50 | 0.198 s | 14.660 s | 1.45 ms |
| zram zstd | 50/50 | 0.219 s | 17.307 s | 1.45 ms |
| Hyperdisk, page-cluster 3 | 50/50 | 0.492 s | 25.860 s | 1.45 ms |
| Hyperdisk, page-cluster 0 | 50/50 | 1.225 s | 31.011 s | 1.32 ms |

The zram lz4 arm stored about 2,998 MiB of original pages in 1,007 MiB of physical memory, a 2.98 ratio. Zstd stored about 3,014 MiB in 705 MiB, a 4.28 ratio, but reclaim took 16.3 seconds versus 11.6 for lz4. Lz4 is the latency-oriented choice here; zstd provides more compression. This single ordered run does not establish a universal compressor winner.

All 250 measured Google wake tasks completed without a recorded failure. Disk readahead zero doubled the median input delay relative to readahead three in this run. That is direct evidence against assuming that zero readahead is always faster for network-backed swap.

Earlier direct-I/O measurements on the same provisioned disk configuration were 1,886 IOPS / 469 microseconds median at 4 KiB queue-depth one and 16,319 IOPS at queue-depth 32. Provisioned aggregate IOPS do not equal single-page latency. The earlier AWS 6,000-IOPS disk measured about 1,505 IOPS / 668 microseconds at queue-depth one; different VM hosts and provisioning prevent a provider-wide causal ranking.

The completed [Titanium 50-session baseline](/reports?sel=rpt_d848a2e0-1a7e-435f-a17e-89c32f30d692) used Z3 with eight vCPUs, 64 GiB RAM and a 3,000 GiB local Titanium SSD. It measured 75.3 microseconds median queue-depth-one read latency and 315,829 IOPS at queue depth 32. Fifty simultaneous default-readahead wakes had 302 ms median input echo with zero failures. This is materially faster disk-only performance than the measured network disks, but the tested Z3's storage alone cost $240/month and its whole VM/boot configuration about $846.97/month. The smaller Hyperdisk purchase is the point of this follow-up; it does not reproduce local Titanium latency. Host RAM, warmed working set and run order differ, so the cross-host input-echo values are descriptive rather than an isolated SSD comparison. The prior baseline's source and raw proof remain in `docs/evidence/titanium50-2026-10-14-*`; it was not rerun.

## Database, OS I/O and swap placement

The Google placement experiment used a fresh scale-100 pgbench database, eight clients, four worker threads, two 30-second passes per layout, with reverse layout order on the second pass. `fsync`, `synchronous_commit` and `full_page_writes` stayed enabled. Competing swap-like direct I/O used 4 KiB random reads/writes, 90% reads, queue depth 32. A separate 150-IOPS random-I/O workload represented OS activity.

| Placement of measured I/O | Pass 1 TPS | Pass 2 TPS |
|---|---:|---:|
| DB, swap and OS-I/O surrogate share a volume | 3,393 | 3,543 |
| OS I/O separate; DB and swap share | 3,580 | 3,550 |
| OS I/O, DB and swap all separate | 5,474 | 5,566 |

Each pass reported zero failed transactions. Separate data disks each had 16,000 IOPS / 400 MiB/s; the shared 512 GiB comparison disk had 32,000 IOPS / 800 MiB/s. The VM and boot disk stayed the same. Equal total data-disk provisioned performance makes this a useful queue-isolation comparison, but per-disk baseline allowances, performance limits and VM bandwidth remain relevant.

An earlier two-layout pass measured average durable transaction latency of 1.281/1.226 ms with DB and swap separate, versus 2.218/2.131 ms sharing a disk. These are complete PostgreSQL transaction times with synchronous durability enabled, not isolated fsync syscall timings. The direct-I/O read measurements above supply the separate block-read latency evidence.

The actual operating-system root was not migrated. “All shared” refers to placement of the OS-I/O surrogate. Therefore this experiment supports separating DB/swap under competing I/O, but is not a boot-volume migration or a full production OS/database placement certification. The small database and short runs do not establish long-run production TPS.

## Filesystem and kernel evaluation

AWS completed two durable pgbench passes per filesystem with competing raw swap-like I/O:

| Filesystem / mount | Pass 1 TPS | Pass 2 TPS |
|---|---:|---:|
| ext4, default mount | 8,015 | 8,790 |
| ext4, noatime | 8,067 | 8,760 |
| XFS, noatime | 8,445 | 9,193 |

All six passes had zero failed transactions. `noatime` alone showed little change. XFS was modestly faster in these short passes, but order/cache effects and a small working set limit the conclusion. This does not justify an automatic production filesystem conversion. Raw-partition swap bypasses the filesystem, so filesystem changes affect the DB, not the swap partition itself.

The measured kernel choices were lz4 versus zstd compression and disk `page-cluster` three versus zero. Transparent hugepages remained in `madvise` mode and swappiness at 60. Explicit cgroup reclaim created parked memory pressure; a swappiness sweep would not measure the same mechanism. No durability controls were disabled and no production kernel parameters were changed.

## Costs

USD list-price estimates, Google us-central1 and AWS us-east-1, 730 compute hours/month. Prices exclude inference, egress, snapshots, taxes and workspace/repository artifacts. The additional shared comparison disk is excluded from the production-like totals.

| Component | Google Hyperdisk / C4 | AWS io2 / m7i |
|---|---:|---:|
| 256 GiB DB capacity alone | $20.48/month | $32.00/month |
| 256 GiB DB at the tested performance | $95.88/month | $422.00/month |
| Separate 256 GiB swap at that performance | $95.88/month | $422.00/month |
| 32 GiB OS disk | $3.88/month | $2.56/month |
| Eight-vCPU VM, 30/32 GiB RAM | $288.60/month | $294.34/month |
| VM + OS + DB + swap at tested performance | **$484.24/month** | **$1,140.90/month** |

Google Hyperdisk Balanced includes 3,000 IOPS and 140 MiB/s per disk. Capacity is $0.08/GiB-month, additional IOPS $0.005/IOPS-month, additional throughput $0.04/MiB/s-month. Thus the 256 GiB disk at 16,000 IOPS / 400 MiB/s is $20.48 + $65 + $10.40. At baseline data-disk performance, the same two 256 GiB disks plus the tested VM/boot configuration total about **$333.44/month**. That cheaper performance setting was not the native scale test configuration.

AWS io2 is $0.125/GB-month plus $0.065 per provisioned IOPS-month in the first 32,000-IOPS tier. Thus each tested 256 GiB / 6,000-IOPS disk is $32 + $390. Higher IOPS tiers apply per volume, not to the aggregate across separate volumes. The official pricing API confirmed Linux shared-tenancy m7i.2xlarge at $0.4032/hour. The distributed-volume figures above exclude the VM, attachments, snapshots, and data transfer.

For scale only, the Google C4 RAM price component is $0.003938/GiB-hour: 256 extra GiB is about $735.93/month of RAM component, compared with $20.48 of baseline Hyperdisk capacity or $95.88 for the tested disk performance. RAM is not sold independently of a compatible VM shape, and swap has different latency and semantics; these are cost components rather than interchangeable capacity quotes.

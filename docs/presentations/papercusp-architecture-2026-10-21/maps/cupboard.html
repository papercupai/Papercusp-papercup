The Cupboard

Make PaperCusp yours

Everything your agents work with — tools, identities, rules, events and more — is something you can make yourself. Keep it private in your own workspace, or share it with everyone through the Cupboard, PaperCusp's shared shelf of things people have made.

  1. Make it locallyAsk your agent, or write it yourself.
  2. Use itIt lives in your workspace. Nobody else sees it until you publish.
  3. PublishPoint the Cupboard at a public GitHub repo, pinned to a commit.
  4. ReviewReviewed kinds are checked before they are listed. The rest list right away.
  5. Others installAnyone can add it to their own workspace from the Cupboard.
  6. Update or delistPush a new commit for a new version, or take it down.

↺ an update goes back through publish and review — the approved version keeps serving while the new one waits.

Two ways to customize

The same things can live in two places. Start local; publish when it is worth sharing.

Local

private · instant

Made in your own workspace and used right away. It stays yours: nothing is listed anywhere until you decide to publish it.

The Cupboard

shared · versioned · reviewed

Published from a public GitHub repo and pinned to a commit, so everyone installs exactly the version that was listed. Most kinds are reviewed before they appear.

Rules

Automatic reactions and guards: run an action when an event happens, or refuse a tool call before it runs.

Make it
Give each rule its own folder, ~/.papercusp/rules/installed/<name>/, holding a rule.json and a listing.json that says "kind": "rule". A guard rule needs schemaVersion, id, title, description, version, "delivery": "sync", "sink": "pre-tool" and a guard with deny or allowOnly. Add tools to limit which tools it watches.
Check it
The file is read against a strict schema. A missing or unknown field makes the rule invalid, and an invalid rule is skipped, never half-applied. cupboard:publish-rule and cupboard:install-rule refuse a rule.json that does not parse.
Turn it on
An installed rule does nothing until an identity pins it. Every session wearing that identity then has the guard checked before each matching tool call.
Share it
Publish it with cupboard:publish-rule.
Review
reviewed

03

Sharing on the Cupboard

Every kind shares the same way: a listing points at your public GitHub repo, pinned to a commit.

  • PublishRun the kind's publish verb (or ask your agent to). Publishing signs you in with your GitHub identity, so every listing has a real author.
  • VersionsA listing is pinned to one commit. Push a new commit and publish again: that is a new version.
  • ReviewReviewed kinds wait for approval before a version is listed. While a new version waits, the previously approved version keeps serving.
  • DelistTake a listing down with cupboard:unpublish. Only the publisher, or a verified claimant of the repo, can do it.

Walkthrough: publish a rule

  1. Keep each rule in its own folder, named after its ref, inside a GitHub repo: 
    my-rules/
  no-force-push/
    rule.json
    listing.json
  2. Push the repo to GitHub and make it public, so the Cupboard can read the folder at the commit you publish.
  3. Publish it, naming the rule and the repo: 
    cupboard:publish-rule {
  "ref": "no-force-push",
  "githubUrl": "https://github.com/you/my-rules"
}
    Rules are a reviewed kind, so the listing appears once an operator approves it.
  4. Anyone can then add it to their workspace with cupboard:install-rule. The other kinds follow the same steps with their own publish verb.

reviewed before listing

Identities, rules, events, recipes, rubrics, plans and goals, datatypes and apps.

listed immediately

Tools (as code-tool packs), plugins, themes and templates. Each is still pinned to a commit.

05

Trust

Review before listing. Identities, rules, events, recipes, rubrics, plans, goals, datatypes and apps are checked before anyone can install them. Tools, plugins, themes and templates list immediately.

Nothing changes under you. Every listing is pinned to a commit in a public repo, so what you install is exactly the code that was listed, and you can read it first.

Only the owner can take it down. Delisting is limited to the publisher or a verified claimant, and every publisher signs in with GitHub.
